# Задача для Claude Design: сигнал-баннер тренера на «Истории» + экран «Замеры» (iOS)

## 0. Что это и зачем

Сервер уже вычисляет состояния методики (свежесть замеров, перерывы, плановая разгрузка,
цель фазы, лимит талии, готовый отчёт недели) — но сегодня они умирают в глубине
rationale тренера. Нужен **информационный баннер на экране «История»** — между плашкой
статистики и карточкой «След. тренировка» — который поднимает наверх ровно те сигналы,
где от атлета требуется действие в ближайшие дни.

Вторая часть задачи — **ввод талии в приложении**: экран «Вес» становится экраном
«Замеры» (вес + талия). Без этого баннеры про замеры вели бы в тупик (талия сейчас
вводится только через MCP-чат) — а мёртвый CTA за пару тапов приучает игнорировать
все баннеры, включая критические.

Таксономия и правила ниже прошли панель критики (UX / методология / архитектура)
и утверждены атлетом. Данные реальные, блок едет в прод.

## 1. Контекст / дизайн-система (уже в проекте)

- iOS, **SwiftUI**, всё на **JetBrains Mono**, язык — русский. Эстетика — liquid-glass
  (`.liquidGlass`/`.glassCard`, чипы-капсулы). Палитра: `--ink/2/3/4`, `--accent #FF4D1F`,
  сигналы `--ok #1F9D6B`, `--warn #D89324`, `--bad #DC4848`, тёплые обои `WarmWallpaper`.
- Экран «История» сверху вниз: TopBar → плашка статистики → **[СЮДА БАННЕР]** →
  карточка «След. тренировка» (с датой-рельсой и чипом фазы) → лента тренировок.
- Экран «Вес»: график с тапом по точкам, inline-ввод, ряд последних записей.

## 2. Таксономия сигналов (утверждена)

Семьи с эскалацией: внутри семьи виден только **старший** сигнал — никогда два упрёка
об одном и том же.

### Семья «замеры» (вес + талия схлопнуты в один баннер)

| id | Триггер | Severity | Текст (смысл) | CTA | Авто-смерть |
|---|---|---|---|---|---|
| `measurements_due` | 10–14 дн без замера (вес и/или талия) | info | «Обнови замеры: вес и талия. Через N дн. советы по калориям встанут на паузу» (+ подпись «ещё пара точек — тренд оживёт», если тренд невалиден) | → Замеры | замер внесён / эскалация |
| `measurements_overdue` | >14 дн (матрица питания реально отключилась) | warn | «Советы по калориям на паузе — внеси вес и талию, вернутся» | → Замеры | замер внесён |

Старт с 10-го дня, не с 7-го: при недельной каденции старт на 7-й день зажигал бы
баннер каждую неделю даже дисциплинированному — гарантированная слепота. В копии
всегда указано, чего именно не хватает: вес / талия / оба.

### Семья «тренировки» (только окна 11+; сигналов «7 дней не был» нет — это нотация без действия)

| id | Триггер | Severity | Текст (смысл) | CTA | Авто-смерть |
|---|---|---|---|---|---|
| `return_soon` | 11–13 дн без тренировки | warn | «Потренируйся до {дата}, иначе следующая сессия — возвратная (~85–90% весов)» | → план | любая тренировка / переход порога |
| `return_mode` | ≥14 дн (протокол возврата активен) | accent | «Возвратная сессия уже облегчена до ~85–90% — просто приди, догонять ничего не надо» | → план | первая завершённая сессия |

Ключевая идея `return_soon`: конкретный дедлайн + конкретная потеря вместо вечного
«план ждёт». `return_mode` — намеренно поддерживающий, не тревожный: момент возврата —
самая уязвимая точка, стыд за перерыв — главная причина не вернуться.

### Контекст фазы

| id | Триггер | Severity | Текст (смысл) | CTA | Авто-смерть |
|---|---|---|---|---|---|
| `deload_week` | плановая разгрузочная неделя (сервер уже считает) | accent | «Разгрузочная неделя: −30–40% объёма, веса рабочие» | → план | первая deload-сессия / конец недели |
| `phase_goal` | цель фазы достигнута — по тренду с гистерезисом, не по одной точке | accent | «Средний вес {X} — цель фазы. Обсуди с тренером переход» | нет (инфо) | смена фазы; снуз до воскресного отчёта, дублируется в отчёте |
| `waist_limit` | талия у жёсткого лимита (фаза набора), по двум замерам подряд | **critical** | «Талия {X} см — у лимита {Y}. Тренер предлагает мини-кат» | → Замеры | замер ниже лимита / смена фазы. **Не снузится** |

### Информация и позитив

| id | Триггер | Severity | Текст (смысл) | CTA | Авто-смерть |
|---|---|---|---|---|---|
| `weekly_report_ready` | свежий (≤48 ч) непрочитанный отчёт недели | info | «Готов отчёт недели» | → шит отчёта | прочтение (серверная отметка) / 48 ч |
| `week_done` | закрытая неделя с ≥90% выполнения плановых подходов (≥2 тренировки по плану) | positive (ok-тон) | «Неделя закрыта: 92% плана. Так держать» | нет | 48 ч; **крестик обязателен** |

Позитив — только за реальное дело (решение атлета). Никаких «тренировка готова»,
никаких пустых стриков. Показывается только когда нет warn/critical.

### Отклонено (не рисовать)

`group_dry` (валидатор плана и так закрывает группы), `stall` как баннер (не решается
за дни — живёт в воскресном отчёте), отдельный баннер про тренд (подпись в семье
«замеры»), «сегодня по ритму тренировка» (отклонён атлетом), любые советы без
серверного состояния (белок/сон — в отчёт и чат).

## 3. Правила показа (жёсткие)

1. **Дефолт главного экрана — без баннера.** Виден максимум 1; второй слот
   открывается только при активном critical.
2. Приоритет `critical > warn > accent > info > positive`; внутри уровня —
   детерминированный порядок: замеры → тренировки → deload → отчёт. Без ротаций.
3. Баннер — чистая функция серверного состояния: состояние снялось → баннер исчез
   в тот же кадр. Гаснет по **действию** (запись веса), а не по переходу на экран.
4. Дисмисс — **крестик** (не свайп: конфликт с жестами над лентой). Ключ дисмисса =
   сигнал + эпизод состояния: «скрыть навсегда» не существует, следующий эпизод
   через месяц покажется снова. Снузы: info 72 ч, accent — до смены эпизода,
   warn 48 ч, positive — крестик до смены эпизода, critical — не снузится.
5. У каждого сигнала есть авто-смерть без участия атлета (см. таблицы). Сигнал без
   авто-выхода в систему не допускается.
6. Тон: тренер «на ты», **последствие и путь назад, никогда вина**. «Через 2 дня план
   придётся облегчить» / «внеси вес — советы вернутся» вместо «ты пропустил».

## 4. Что нарисовать (макеты в контексте экрана «История»)

1. **Один info-баннер** (замеры): компактный, иконка-глиф слева, заголовок + одна
   строка тела, стрелка/CTA справа, крестик в углу. Не должен спорить с карточкой
   «След. тренировка» за внимание — она главный элемент экрана.
2. **Warn** (`return_soon` с дедлайном и `measurements_overdue`) — warn-тон рамки/глифа.
3. **Critical** (`waist_limit`) — bad-тон, без крестика; единственный случай
   **двух баннеров** одновременно (critical + warn под ним).
4. **Accent** (`return_mode`, `deload_week`) — поддерживающая, не тревожная подача.
5. **Positive** (`week_done`) — ok-тон, с крестиком.
6. **Длинный текст** (2 строки тела) и минимальная ширина (SE).
7. Появление/исчезновение (лёгкая анимация: вставка сверху, fade+collapse при гашении).

## 5. Экран «Замеры» (вторая часть макета)

Экран «Вес» расширяется до «Замеры»: две метрики — вес (кг) и талия (см).
- Переключатель метрики (сегмент «Вес | Талия») над графиком; паттерны те же:
  график с точками, тап по точке — удаление, inline-ввод снизу.
- Для талии подпись-подсказка при вводе: «утром натощак, по пупку».
- Deep-link из баннеров замеров ведёт сюда (если просрочен только один — сразу на
  нужный сегмент).
- Пустое состояние талии: «Первый замер станет базой фазы».

## 6. Техническая реализация (для исполнителя, не для макетов)

### Backend (новый модуль `backend/coach_signals.py`)

- `GET /api/coach/signals` → `{ok, generated_at, signals: [...]}` — список собирается
  **на лету** из SQLite + coach_state (всё локально, без LLM), уже схлопнутый,
  отсортированный и отфильтрованный от активных снузов. Никакого кэша.
- Формат сигнала: `{id, instance_key, severity: info|accent|warn|critical|positive,
  title, body, action: {type, label} | null, snoozable: bool}`.
  `action.type` — закрытый enum: `open_measurements | open_next_workout |
  open_weekly_report | none`.
- `instance_key = "<id>:<определяющий факт из БД, UTC ISO>"`
  (например `measurements_due:weight=2026-08-05`). Смена факта или эскалация id —
  новый экземпляр: старые снузы не действуют, сигнал оживает сам.
- `POST /api/coach/signals/dismiss {instance_key, snooze_hours?}` → снузы в новой
  SQLite-таблице `signal_snoozes`; critical → 409.
- `POST /api/reports/weekly/read` — серверная отметка прочтения отчёта
  (гасит `weekly_report_ready` и для MCP-чата, и после переустановки).
- Талия: `GET/POST/DELETE /api/waists` поверх готовых store-методов
  (`list_waists/save_waist/delete_waist`) — по образцу `/api/body-weights`.
- Все дельты времени и тексты считает **сервер** («вес не обновлялся 9 дней»);
  клиент никогда не сравнивает даты и не сочиняет текстов.
- `week_done`: по `adherence`-агрегату за прошедшую неделю (≥2 тренировки по плану,
  ≥90% плановых подходов).

### iOS

- `SignalBannerView` на «Истории» между статистикой и карточкой плана; рендерит
  первые 1–2 сигнала из ответа.
- Refetch: `onAppear` Истории, возврат в foreground, pull-to-refresh, и сразу после
  успешных мутаций (вес/талия записаны, тренировка сохранена, отчёт открыт).
  Фонового поллинга и пушей нет.
- Optimistic hide: статическая карта мутация→сигналы (вес/талия →
  `measurements_*`; тренировка → `return_*`; отчёт → `weekly_report_ready`) прячет
  баннер в тот же кадр, затем refetch за истиной.
- Неизвестный `id`/`severity` → generic info-баннер с серверным текстом; неизвестный
  `action.type` → баннер без кнопки (таксономию можно наращивать без релиза iOS).
- Экран «Замеры»: сегмент вес/талия, модели `WaistEntry` по образцу
  `BodyWeightEntry`.

### Наблюдаемость (анти-слепота)

Сервер логирует эпизоды (показан → дисмисснут / выполнен CTA / умер сам) в лог-таблицу.
Правило ревизии: если какой-то сигнал виден чаще чем в ~40% открытий две недели
подряд — поднимать его пороги.

## 7. Фазирование

- **MVP (этот заход):** семьи «замеры» и «тренировки», `deload_week`,
  `weekly_report_ready`, `week_done` + экран «Замеры» + оба эндпоинта + снузы.
- **Сразу за ним:** `phase_goal`, `waist_limit` (оживают, когда появятся данные
  талии и закончится фаза А).
- **Не делаем:** пуш-уведомления, фоновый поллинг, советы без серверного состояния.

## 8. Приёмка

1. Свежие замеры, тренировка вчера → на «Истории» **нет баннера**.
2. 11 дней без замера веса → info-баннер с обратным отсчётом; запись веса гасит его
   в тот же кадр; талия при этом просрочена → баннер остаётся, но говорит только
   про талию и ведёт на её сегмент.
3. 12 дней без тренировки → `return_soon` с датой-дедлайном; тренировка сохранена →
   баннер исчез; 15 дней → вместо него `return_mode` (accent), гаснет после
   первой сессии.
4. Крестик на info → баннер скрыт; наступила эскалация → показался снова
   (новый эпизод, снуз не действует).
5. Разгрузочная неделя → accent-баннер до первой deload-сессии; в воскресенье
   при готовом отчёте показывается отчёт, deload уступает.
6. Неделя с 92% плана и 2+ тренировками → positive с крестиком, сам исчезает
   через 48 ч.
7. `GET /api/coach/signals` без сессии → 401; dismiss critical → 409.
