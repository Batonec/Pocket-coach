# Trainer Business Logic

## 1. Зачем нужен этот документ

Этот документ фиксирует текущее продуктовое поведение `Trainer`:

- как приложение авторизует пользователя;
- какие данные считаются источником истины;
- как устроены экраны `Trainings`, `Progress`, `Weight` и flow создания тренировки;
- какие инварианты должны быть зафиксированы в тестах;
- что сейчас считается частью продукта, а что сохранено в коде, но отключено в UI.

Технические детали окружения, запуска и деплоя лежат в:

- [backend/README.md](./backend/README.md)

## 2. Общая модель продукта

`Trainer` — это backend API на SQLite + нативный iOS-клиент.

В текущей версии:

- справочник упражнений загружается из JSON;
- сохранённые тренировки и вес тела хранятся на backend;
- черновик новой тренировки и часть UI-состояний живут локально на клиенте;
- одна база используется для нескольких пользователей, но данные изолированы по `user_id`;
- основной режим — нативный iOS-клиент (personal-build, фиксированный пользователь);
- браузерный debug-режим нужен для локальной разработки и отладки.

**Правка истории меняет данные, но не переключает состояния.** Правило шире одной фичи.
Запись, правка и удаление прошлого меняют факты, из которых считаются производные: объёмы,
тренды, рекомендация. Но «состояние прямо сейчас» — открытое событие (§4.5), применённый
план, начатая сессия — переключается только действием, совершённым сегодня. Поэтому
сегодняшняя тренировка закрывает открытое событие, а та же тренировка, записанная задним
числом или отредактированная завтра, — нет; поэтому удаление тренировки не открывает
событие заново.

## 3. Режимы пользователя и сессии

### 3.1. Native iOS fixed user

Основной режим. Нативный iOS-клиент работает без внешней авторизации:

- iOS отправляет `shell=ios` и `native_user_id=3` в `POST /api/session/resolve`;
- backend находит пользователя с таким `id`;
- backend выдаёт подписанную cookie `trainer_session`;
- дальнейшие workout/body-weight endpoints работают в контексте этого `user_id`.

Это сознательный personal-build режим. Он не предназначен для публичного multi-user доступа.

### 3.2. Browser debug user

Для локальной разработки браузер без сессии может автоматически получать debug-сессию
(при `MINIAPP_ALLOW_DEBUG_USER=1` или `MINIAPP_DEV_MODE=1`):

- по умолчанию используется alias `browser-default`, если не задан другой;
- данные debug-user живут отдельно.

## 4. Основные сущности

### 4.1. Упражнение

Упражнение из справочника содержит:

- `id`
- `name`

### 4.2. Подход

Подход содержит:

- `set_index`
- `weight`
- `reps`
- `effort`
- `notes`
- `rir`

`effort` — это нормализованная дискретная оценка тяжести:

- `easy`
- `ok`
- `hard`
- `null`

На UI это отображается как:

- `🙂`
- `😐`
- `😣`

`notes` — свободная заметка к конкретному подходу: «канат вместо прямой ручки», «стопы
выше», «узкий хват». Она объясняет вес, а не самочувствие: `exercise_id` не задаёт
установку целиком, и без заметки переход на другую ручку читается коучем как откат силы.
Из заметки не считается ни одного числа — это текст для промпта и для перечитывания в
истории.

`rir` — записанный запас в повторах (0–4), обычно у последнего подхода упражнения; он
точнее значков усилия, и промпт отдаёт приоритет ему. iOS этого поля не вводит, но обязан
вернуть его при сохранении: частичного апдейта у API нет, тренировка уезжает объектом
целиком, и неизвестное клиенту поле молча стёрло бы значение, записанное не из приложения.

### 4.3. Тренировка

Тренировка содержит:

- `id`
- `client_id`
- `workout_date`
- `created_at`
- `updated_at`
- `data.load_type`
- `data.exercises`
- `data.notes`

`data.notes` — одна свободная заметка на всю сессию: «спал 4 часа, всё шло тяжело», «зал
забит, жим ногами не попал». Как и заметка к подходу, она только текст: ни одного числа из
неё не считается.

### 4.4. Запись веса тела

Запись веса тела содержит:

- `id`
- `entry_date`
- `weight`
- `created_at`
- `updated_at`

Для одного пользователя на одну дату существует только одна актуальная запись. Повторное сохранение на ту же дату обновляет значение, а не создаёт дубль.

### 4.5. Событие

Событие — период **без** тренировок с причиной («болел», «командировка»). Оно содержит:

- `id`
- `start_date`
- `end_date` (может быть `null`)
- `text`
- `created_at`
- `updated_at`

Правила модели:

- `end_date = null` означает «событие идёт прямо сейчас». Такое событие **одно**: второе
  открытое backend не создаёт и не даёт получить правкой (`400` с причиной) — иначе
  автозакрытие тренировкой не смогло бы выбрать, какой период закрывать.
- Будущие даты запрещены с обоих концов: событие описывает то, что уже случилось.
  `end_date` не может быть раньше `start_date`.
- Ключа дедупликации у события нет: событий подряд может быть несколько (болезнь → сразу
  командировка), в том числе с одной датой начала. Повторный `POST` создаёт вторую запись,
  а не обновляет прежнюю.
- Категорий и тегов в данных нет — только текст; пресеты в UI подставляют его в поле.
- **Из событий не считается ни одного числа.** Ни счётчиков «дней болезни за месяц», ни
  графиков, ни фич коуча: событие уезжает в промпт тренера текстом и больше нигде не
  участвует.

**Правило дня.** День *с* тренировкой описывается заметкой к тренировке, день *без* —
событием. Одно обстоятельство не должно попадать в оба канала: тренер прочитает это как
два разных факта.

**Автозакрытие.** Создание тренировки сегодняшним числом закрывает открытое событие концом
«вчера»: перерыв кончился в тот день, когда атлет снова пришёл в зал. Событие, начавшееся
сегодня, схлопывается в один день, а не в конец раньше начала. Закрытие молчаливое — тоста
нет, клиент просто перечитывает список. Правка старой тренировки, запись задним числом и
удаление тренировки состояние не переключают (§2): удалённая тренировка событие не
переоткрывает.

**Ручное закрытие.** Автозакрытие не покрывает зазор «потренировался вечером, записал
утром», поэтому есть закрытие в один тап — «Закончилось» в карточке ленты и «Закончилась?»
в плашке «Сегодня». Оно ставит тот же вчерашний день (или день начала, если событие
началось сегодня) и подтверждения не спрашивает.

**API.** `GET /api/events` · `POST /api/events` · `PUT /api/events/{id}` ·
`DELETE /api/events/{id}`. `POST` всегда отвечает `201` (дедупа нет), `PUT` и `DELETE` —
`200` либо `404`, нарушение правил модели — `400` с причиной. Любая из трёх мутаций
запускает фоновую перегенерацию рекомендации (§8.9). Те же операции доступны из чата с
тренером через Coach MCP (`coach_list_events` / `coach_add_event` / `coach_update_event` /
`coach_delete_event`): запись события из разговора — штатный сценарий, а не отладка.

### 4.6. Обхват тела

Метрики цели из vision — рука, плечи, грудь — и протокол стратегии (шея, бедро, ягодицы,
предплечье; рука в двух протоколах, расслабленно и в напряжении) хранятся в таблице
`measurements`: `entry_date`, `kind` (ключ из `limits.MEASUREMENT_KINDS`), `value_cm`,
заметка. Один замер вида в день, повторный за ту же дату перезаписывается. Талия сюда
не входит: у неё своя таблица, лимиты и матрица питания.

Границы одни на все виды — 10–200 см (`limits.MIN/MAX_CIRCUMFERENCE_CM`): они отсекают
описку, а правдоподобность конкретного обхвата — суждение атлета и тренера. Обхваты не
обесценивают совет тренера: план их не читает. Их читает недельный отчёт — по каждому виду
последний замер, дней с него и предыдущий; периодичность протокола (рука раз в 4 недели,
остальное раз в 8) модель берёт из главы «Измерения» стратегии, сервер её не судит.

**API.** `GET /api/measurements` (отдаёт и словарь видов) · `POST /api/measurements` ·
`DELETE /api/measurements/{id}`. iOS-клиент экрана обхватов пока не имеет: штатный ввод —
из чата с тренером через Coach MCP (`coach_add_measurement` / `coach_list_measurements` /
`coach_delete_measurement`).

## 5. Источники данных

### 5.1. Справочник упражнений

Источник:

- [backend/resources/exercises.json](./backend/resources/exercises.json)

Используется для:

- основной подборки и каталога «Добавить упражнение»;
- preview- и draft-карточек в `New Workout`;
- селектора упражнения на экране `Progress`.

### 5.2. Серверные тренировки

Источник истины для:

- истории тренировок;
- экрана `Progress`;
- reference-строк `прошлое выполнение → план`;
- быстрого planned add;
- кольцевого прогресса вокруг FAB.

Источник:

- SQLite backend;
- таблица тренировок текущего пользователя.

### 5.3. Серверные записи веса тела

Источник истины для экрана `Weight`:

- SQLite backend;
- таблица `body_weights`.

### 5.4. Что хранится локально

В `localStorage` живут только UI-состояния:

- черновик тренировки;
- текущая вкладка;
- выбранный диапазон на `Progress`;
- выбранный диапазон на `Weight`;
- выбранное упражнение на `Progress`.

Сохранённые тренировки и записи веса тела не считаются локальным источником истины.

## 6. Навигационная модель

Нижний бар состоит из трёх вкладок:

- `Trainings`
- `Progress`
- `Weight`

Создание новой тренировки не является отдельной вкладкой.

Новая тренировка открывается:

- по FAB `+` на `Trainings`;
- либо через возврат в уже существующий черновик.

По умолчанию приложение открывается на `Trainings`.

## 7. Правила сортировки данных

### 7.1. Сортировка тренировок

Тренировки сортируются:

1. по `workout_date` по убыванию;
2. при совпадении даты — по `created_at` по убыванию;
3. затем по `updated_at` по убыванию;
4. затем по `id` по убыванию.

Это правило используется в:

- `Trainings`;
- логике поиска последнего выполнения упражнения;
- аналитике прогресса.

### 7.2. Сортировка записей веса тела

Записи веса тела для графика упорядочиваются от старых к новым.

## 8. Экран Trainings

### 8.1. Назначение

Экран показывает историю тренировок текущего пользователя.

### 8.2. Состав карточки тренировки

Карточка включает:

- дату и день недели в одной строке;
- компактный список упражнений;
- сгруппированное summary по сетам;
- заметки к подходам — строкой под упражнением, если они есть;
- заметку ко всей тренировке — последней строкой карточки, если она есть.

`load_type` хранится в данных тренировки (из применённого плана тренера; без плана — `null`, см. §9.19), но текущий UX истории не показывает отдельный `heavy / medium / light` badge.

### 8.3. Формат summary по сетам

Подходы группируются по последовательным одинаковым весам. Внутри такой группы повторения схлопываются в компактную строку.

Примеры:

- `60кг ×14`
- `60кг ×14×3`
- `90кг ×13×2, 12`

Если у подходов есть `effort`, он приклеивается к соответствующей компактной группе.

Если у подходов есть `notes`, они выводятся отдельной компактной строкой под упражнением:
заметки подходов склеиваются через ` · `, одинаковый текст на нескольких подходах
схлопывается в одну запись (постановка одна, а «канат · канат · канат» — шум, а не три
факта), строка приглушена и обрезается по двум строкам. Заметка ко всей тренировке (`data.notes`) показывается ниже, отдельной
строкой под списком упражнений. Карточка истории — единственное место, где заметки
читаются: текст, который нельзя перечитать, незачем и вводить.

### 8.4. Swipe actions

Карточка тренировки поддерживает свайп влево и открывает три действия:

- удаление (через alert);
- редактирование;
- заметку — поздний вход в текст сессии, когда полоска после сохранения уже уехала (§8.10).

Карточка должна уметь закрываться назад:

- свайпом вправо;
- тапом по свободной области.

Тап по карточке тренировки по-прежнему ничего не делает. У карточки события правила
другие: свайп влево даёт единственное действие «Удалить» (через alert), а тап открывает
правку — только там текст события виден целиком и правятся уехавшие даты.

### 8.5. FAB на экране истории

Внизу справа расположен FAB:

- если черновика с реальными сетами нет, это обычный `+`;
- если живой черновик есть, FAB становится входом обратно в него.

Если есть живой черновик, вокруг FAB показывается кольцевой прогресс по основной шестёрке упражнений.

Этот прогресс считается дробно:

- по упражнениям основной шестёрки;
- по количеству выполненных planned sets внутри каждого упражнения;
- а не просто по факту “в упражнении появился хотя бы один сет”.

### 8.6. Next workout plan

В коде существует генератор `next workout plan`, но текущий UI его не показывает.

Фича отключена флагом:

- `ENABLE_NEXT_WORKOUT_PLAN = false`

### 8.7. Совет тренера (LLM-рекомендация)

Отдельная фича поверх эвристик: backend строит план **следующей** тренировки по истории
пользователя через Claude API и кэширует его (одна актуальная рекомендация на пользователя).

- **Состав рекомендации** повторяет тренировку: `exercises[]` с `exercise_id`/`name`/`note`
  и `sets[{reps, weight}]`, плюс `focus`, `load_type` (heavy/medium/light) и развёрнутый
  `rationale` — текстовое объяснение, почему выбран именно такой состав и нагрузка, а не другой.
- **Только каталожные упражнения.** `exercise_id` ограничен enum'ом из 12 упражнений на уровне
  JSON-схемы; на сервере результат дополнительно валидируется (выдуманные id отбрасываются,
  reps/weight приводятся к разумным границам, имя берётся из каталога).
- **Цели объёма по группам.** По умолчанию все крупные группы делят один коридор недели блока
  (ramp/deload), малые держат свои потолки политики. Программа с приоритетами (спина 16 сетов,
  квадрицепс 9) так не выражается, поэтому фаза может задать `group_targets` —
  `{группа: [min, max]}` с ключами строго из `coach_features.MUSCLE_GROUPS`. Это объём ЗРЕЛОГО
  блока: на неделях разгона идут к нему снизу, ориентир недели приходит из блока ПРОГРАММА в
  промпте. Неизвестная группа отвергается на записи — опечатка иначе молча не применилась бы.
- **Каркас — ротация, объём — за круг.** Сплит Д1–Д4 стратегии написан под четыре тренировки в
  неделю, атлет ходит через день, и календарные недели чередуются 4/3. Поэтому промпт
  (`program_header` в `user_blocks.md`) объявляет каркас ротацией без привязки к неделе:
  следующая сессия берёт день за последним сыгранным, ротация держится при темпе не ниже трёх в
  неделю (6 тренировок за 14 дней), ниже — фулбади по дефициту круга. Объём против
  `group_targets` судится за КРУГ из четырёх последних тренировок (`coach_features.round_volume`,
  блок «Объём за КРУГ»), блок за 7 дней остаётся темпом без целей; предусловия застоя считают
  объём за круг тем же способом (сеты активного окна на число кругов в нём). Блок явки к неделям
  добавляет темп за 14 дней и интервалы между последними сессиями; серия недель «по четыре» из
  промпта убрана. Политика промпта просит не ставить две тренировки подряд без просьбы атлета
  (rest_days по умолчанию 2) — ритм записан в профиле. iOS по-прежнему рисует цели недели против
  объёма календарной недели (`coach_context.group_targets`) — известное расхождение с промптом.
- **Память карточки о себе.** В промпт плана уходит прошлая карточка из кэша (`previous=` —
  строка `recommendations`; её payload переживает `pending`): фокус, нагрузка, состав, была ли
  по ней тренировка (`based_on_workout_id` против id в истории) и пункт «Совет» из её rationale —
  обещание следующей сессии. Политика просит держать преемственность и называть причину смены
  линии; сам rationale просит заканчивать «Советом» о следующей сессии. Канал включает вызывающий,
  как и события: `server.py`, `refresh_recommendation.py` и Coach MCP передают строку кэша,
  тесты проверяют каждого (`test_previous_card.py`).
- **Матрица питания считает по темпу фазы и по контуру коррекции стратегии.** Все ветки
  строятся от коридора `rate_kg_per_week` (он есть у каждой фазы), а не от её имени, с полосой
  нечувствительности ±0.12 кг/нед (абсолютной, `RATE_TOLERANCE`): тренд в коридоре → не
  трогать; выше/ниже коридора → шаг калорий режима — 150 на срезе, 75 на наборе, 100 на
  удержании (`CALORIE_STEP_KCAL`; на наборе — «или пауза набора», на срезе — «или неделя
  поддержки»), но только когда отклонение подтверждают и МНК-наклон за окно, и разница 7-дневных
  средних с интервалом в окно подтверждения — две недели на срезе и удержании, четыре на наборе
  (`CONFIRM_WINDOW_DAYS*`) — без второго свидетеля матрица называет отклонение и просит
  взвешиваться ежедневно. «Вес стоит всё окно» читается по фазе: на срезе → снизь калории (талия
  вниз — рекомп-бонус, не трогать), на удержании — выполненная задача этапа, на наборе → добавь.
  Промпт чисел шага не повторяет: он просит перевести ветку своими словами, числа не меняя. Тренд — наклон прямой по всем
  замерам окна, а не разница крайних точек: одно тяжёлое утро больше не задаёт неделю. В
  строке замеров стоит число взвешиваний за 7 дней и напоминание, что для недельной
  средней нужно ≥4; когда точек хватает, сама 7-дневная средняя названа числом рядом со
  средней неделей раньше.
- **Недели поддержки.** Внутри дефицита стратегия ставит неделю на уровне TDEE (четыре
  недели дефицита → одна поддержки, либо по стоп-сигналу). Атлет отмечает её руками
  (`coach_mark_support_week` в Coach MCP; в `coach_state.json` это `support_weeks` —
  понедельники недель). Её замеры не входят ни в тренд, ни в 7-дневные средние матрицы и
  ни в калибровку TDEE; пока идёт сама неделя и ещё 14 дней после (окно подтверждения
  матрицы) советов по калориям нет — вес на ней стоит или растёт по плану, и это не плато.
  План и отчёт получают флаг в контексте: тренировки в обычном режиме, это не разгрузка.
- **Свежесть.** Рекомендация помечается `stale`, если появилась тренировка новее той, по которой
  она построена. После создания/изменения/удаления тренировки она перегенерируется в фоне.
  После успешного удаления iOS сразу переводит план в `pending` и принимает только результат,
  построенный по оставшемуся числу тренировок и новому latest workout id; старый ответ до
  удаления не может завершить polling. Если удалена последняя тренировка, backend удаляет
  актуальный кэш рекомендации (audit-log сохраняется), а iOS переходит в `none` и сбрасывает
  незапущенный план.
- **iOS UX.** Карточка «Совет тренера» вверху экрана `Trainings`: читается мгновенно из кэша
  (вне 3-сек дедлайна загрузки), «Обновить» запускает синхронную генерацию (10–40 с, оверлей).
  Состояния: `none` / `pending` / `ready` (+ `stale`) / `failed`.
- **Применение как план.** «Применить в план» делает совет планом (`appliedPlan`), НЕ
  выполненными подходами: тренировка не считается начатой, пока не записан первый сет.
  Карточки идут в порядке рекомендации с целями «вес × повторы», заголовок секции —
  «План от тренера» (+ «Сбросить»; превью-карточку можно убрать из плана long press-ом).
  Кнопка совета в применённом состоянии — «В плане ✓», для изменившегося совета —
  «Применить новый» (заменяются только цели, записанные сеты не трогаются).
- **Следующий подход по «+»** (единый приоритет и для конструктора): последний кастомный
  подход повторяется → цель применённого плана по индексу → история +1 повтор → 12×0.
  Long press по «+» открывает конструктор подхода.
- **Связка с тренировкой.** При сохранении новой тренировки с применённым планом в payload
  пишется `data.recommendation` — снапшот совета (без rationale/notes) для статистики
  «факт vs план»; сервер сохраняет снапшот при последующих PUT-редактированиях. После
  сохранения план очищается, рекомендация перегенерируется в фоне.
- **Источник данных для модели** — вычисляемые фичи вместо сырой истории: per-exercise
  сводки за всю историю (топ-сет, e1RM, дата последнего ПР, % от пика; гравитрон
  инвертирован; у каждой сессии в сводке — позиция упражнения `[#k/n]`), объёмы за 7 дней
  (темп) и за круг из четырёх тренировок прямыми и эффективными сетами (жимы добирают
  трицепсу/дельтам, тяги — бицепсу; цели по группам — в прямых и за круг, эффективные подписаны
  как справочные), явка по календарным неделям с темпом за 14 дней, прошлая карточка тренера,
  флаг застоя с предусловиями по активному окну блока (от старта фазы или возврата после
  перерыва, отпуск в окно не входит; порог объёма — нижняя граница `group_targets`; застой —
  ≥4 недель без прироста внутри окна), ступени возврата к доперерывному рабочему весу,
  тренды веса и талии с веткой матрицы питания; сырыми подаются только последние ~10
  тренировок с пометками тяжести (`-`/`+`) и опциональным RIR (`@N`).
- **События и заметки — единственный свободный текст в промпте.** Слова атлета едут
  дословно и в «ёлочках»: заметка к подходу стоит вплотную к своему подходу (она объясняет
  именно его вес), заметка к сессии — после тире в хвосте строки, хроника событий — не
  отдельным списком, а вперемешку с сырой историей, ровно в том разрыве дат, который
  объясняет; открытое событие дополнительно уезжает в блок `КОНТЕКСТ` сразу за днями
  простоя. Из этого текста не считается ни одной фичи и не добавлено ни одной проверки в
  валидатор: методика «после болезни возвращайся как после перерыва, даже если дней меньше
  14» — фраза в `backend/prompts/next_workout.md`. Хроника хранится без окна по датам, страховка
  одна — потолок в 40 строк (режутся самые старые), и об обрезке промпт говорит вслух.
  В недельном отчёте события идут отдельным блоком: пересекающиеся с периодом, а если их
  нет — прямой строкой «пропуски ничем не объяснены». Заметки печатаются в сырой истории
  всегда; события доезжают до обоих промптов — и плана, и отчёта. Канал включает только
  переданный `events=`, поэтому все живые вызыватели модели (`server.py`,
  `refresh_recommendation.py`, `weekly_report.py`) закрыты тестами; у Coach MCP теста нет —
  там проверка глазами, в `coach_preview_prompt`.
- **Фазы подготовки.** Методика ведётся фазами `cut_recomp` / `lean_bulk` / `maintenance`
  (+ вычисляемый режим «возврат после перерыва» при паузе ≥14 дней). Состояние фазы —
  `coach_state.json` рядом с базой; переключение только руками через Coach MCP
  (`coach_set_phase`), при достижении цели фазы модель лишь предлагает смену в rationale.
  Недельный объём строительных фаз растёт ramp'ом 6–8 → потолок фазы; maintenance — одна
  fullbody heavy сессия в неделю (8–12 подходов), объём не растёт, веса не снижаются.
- **Возврат после перерыва: без прогрессии.** Методику возврата ведёт модель — сервер
  не зашивает ни процентов снижения, ни физиологических обоснований: это тренерское
  суждение, которое устаревает и зависит от контекста (длина паузы, профиль, восстановление).
  Алгоритмический слой отвечает за факты и за одну границу. Факты: рабочие веса каждого
  упражнения в последней сессии ПЕРЕД перерывом (плюс оговорка, что отметки усилия и RIR
  в истории описывают ту же доперерывную форму) и — на сессиях после возвратной — ступени
  возврата к этому доперерывному рабочему, а не к историческому пику (шаг стека из истории,
  печатаются пока вес не возвращён и возврат моложе 8 недель) — данные-ориентир, не
  валидируемая рамка. Граница: вес возвратной сессии не может
  превысить доперерывный рабочий ни по одному движению. Насколько уйти ниже этой границы
  и как быстро возвращаться — решает модель.
- **Талия как вторая метрика.** Замеры талии (см) хранятся в таблице `waists` и пишутся
  через Coach MCP. Единый диапазон записи и аналитики — 50–160 см: выход за него
  отклоняется до сохранения, а legacy-мусор не считается свежей точкой. Правило
  свежести общее с весом (>14 дней — советы по калориям не даются). Решение по
  калориям вычисляет сервер по матрице «тренд веса × тренд талии» per phase — модель
  только формулирует готовую ветку. Форма iOS держит ввод даты и числа в локальном
  состоянии sheet и публикует их в общий store один раз при сохранении; это не даёт
  графику и всему экрану «Замеры» перестраиваться на каждое нажатие клавиши. Открытие
  формы тоже не мутирует общий store: начальные дата и значение вычисляются локально до
  первого кадра sheet. Decimal-клавиатура один раз прогревается за loading screen, а
  нативное числовое поле становится first responder сразу после присоединения к окну,
  поэтому клавиатура начинает появляться вместе с формой и не требует отдельного тапа.
  Сам введённый символ остаётся в `UITextField` мгновенно; обновление SwiftUI-валидации
  схлопывается с паузой 120 мс, а сохранение всегда читает актуальное значение напрямую
  из input buffer. Экран с графиком под sheet игнорирует изменение keyboard safe area.
  Сохранение или удаление веса/талии сразу обновляет локальный экран замеров, заново
  запрашивает детерминированные coach signals и запускает фоновую перегенерацию
  LLM-рекомендации, если у пользователя уже есть история тренировок. Быстрые правки
  схлопываются: параллельных генераций для одного пользователя нет, но последнее
  изменение не теряется. Если изменение запустило генерацию, весь список баннеров
  сразу скрывается и остаётся пустым при `pending`; более старые параллельные ответы
  игнорируются. После итогового `ready`/`failed` сервер заново рассчитывает все
  семейства сигналов. Это gate жизненного цикла: условия и severity баннеров остаются
  алгоритмическими, а LLM их не выбирает. Аналитические
  экраны iOS сохраняют старые коридоры до
  готовности нового payload, но экран «Сегодня» скрывает старый план и кнопку старта,
  пока обновление не завершится. Ошибка генерации также не возвращает старый план:
  остаётся карточка ошибки с повтором. Новый план применяется автоматически только
  до первого реального подхода; начатая тренировка сохраняет цели до конца сессии.
- **Гормональный контекст — только в профиле.** Планировщик по недельному циклу
  инъекций удалён: фон супрафизиологичен всю неделю, и попытка таймить heavy-дни по
  дню цикла — спекуляция, которая только связывала модели руки. Гормональный контекст
  атлета живёт прозой в профиле как фактор восстановления; медицинская граница
  (никаких советов по ГЗТ/дозировкам/анализам) осталась в промптах и MCP-инструкциях.
- **Семантический валидатор** поверх JSON-схемы проверяет ровно три жёсткие границы:
  покрытие групп (крупная группа или бицепс бедра, сухие ≥10 дней, обязаны попасть в
  план), возвратный потолок весов (см. выше) и потолок размера сессии — верхняя граница
  `session_sets` текущей фазы (нижняя не проверяется: короткая сессия может быть
  решением). Всё остальное — диапазоны повторов, шаги весов, чередование
  heavy/medium/light, `rest_days` (клампится 0–4 молча) — тренерское суждение модели,
  направляемое ориентирами промпта, но не валидируемое. Нарушение жёсткой границы
  возвращается модели одним авто-репромптом; повторный промах сервер разрешает
  детерминированно (возвратные веса клампятся к доперерывным, лишние подходы режутся с
  хвоста плана по одному на упражнение и не ниже одного подхода, незакрытое покрытие
  честно дописывается в rationale) — генерация из-за методики больше не падает в
  `failed`.
  Имя упражнения модель не пишет вовсе: сервер подставляет каталожное по id.
  Дубль каталога (id 1 ≡ id 18) слит на этапе сериализации: модель видит и может
  ставить только id 18.
  Правила — текст в `backend/prompts/plan_rules.md`: блок правила несёт формулировку (она
  уходит в системный промпт, блок «ЖЁСТКИЕ ГРАНИЦЫ») и четыре ключа для сервера — «для»
  (область: сухая группа, подход с возвратным потолком, план с потолком сессии), «требует»
  (условие), «нарушение» (строка для репромпта), «починить» (присваивание или процедура).
  Исполняет их `rule_engine`, слова объявлены словарём в `plan_validator`; модель читает ровно
  тот блок, который сервер исполняет. Пометки «Проверка методики» для атлета —
  `backend/resources/plan_notes.md`.
  Форма ответа (типы, клампы, каталожные имена) — `rules.normalize_model_plan`, это гигиена,
  а не методика.
- **Плановый deload.** После 6 недель реально накопленной работы в блоке (≥2 сессии/нед)
  сервер помечает следующую неделю разгрузочной (флаг в контексте промпта; объём и веса
  лёгкой недели задаёт стратегия атлета, промпт и баннер чисел не повторяют; после неё ramp
  объёма начинается заново); как именно
  построить лёгкую неделю — решение модели, валидатор её не ограничивает. При редкой
  посещаемости флаг не ставится — лёгкие недели уже случились сами.
- **Дисциплина как вход тренера.** Сервер агрегирует «факт vs план» за 30 дней (в т.ч.
  какие упражнения стабильно пропускаются целиком) — модель адаптирует план к реальному
  поведению (пропускаемое — раньше в сессии, реалистичный размер плана), без нотаций.
- **Недельный отчёт** (`coach_weekly_report` в Coach MCP): Markdown-ретроспектива —
  итоги недели против целей (начиная с фокуса прошлого отчёта: что сделано, что нет), ПР и
  движение весов по сводке тренажёров, тренды веса/талии по 7-дневной средней с веткой
  матрицы, обхваты и оценка TDEE, дисциплина, курс к цели (четыре вопроса атлета: где он на
  пути к цели, в графике ли стратегии, всё ли хорошо — ПО ПЛАНУ / ОТСТАЁТ / ОПЕРЕЖАЕТ, что
  скорректировать), гейт этапа (критерии выхода по одному, ВЫПОЛНЕН / НЕ ВЫПОЛНЕН с фактом;
  этап переключает только атлет) и фокус следующей недели. Генеральная задача отчёта —
  курс к долгосрочной цели, а не только неделя; промпт — `prompts/weekly_report.md`. В промпт
  уходит и траектория фазы с её старта — вес, талия, темп, ПР, цель по весу: отчёт живёт в
  семи днях, а гейт — в месяцах. Период — всегда последняя **закрытая** календарная неделя (пн–вс),
  а не «последние 7 дней»: дату считает `coach_state.last_closed_week_end`, поэтому
  воскресная вечерняя тренировка попадает в отчёт о своей же неделе, а в воскресенье
  отчёт ещё описывает предыдущую. Кэшируется в `coach_reports`: таймер в ночь на
  понедельник генерирует отчёт заранее, инструмент отдаёт его мгновенно и без токенов
  (`fresh=true` — перегенерация той же закрытой недели). iOS показывает последний отчёт
  кнопкой на «Прогрессе», а весь кэш — экраном «Все отчёты» (`GET /api/reports/weekly/history`);
  правила строк и отметки о прочтении — в docs/WEEKLY_PROGRESS.md.
- **Журнал фаз.** Смена фазы закрывает уходящую записью `{phase, started, ended}`;
  `coach_phase_summary` в любой момент считает итоги текущей или закрытой фазы из
  истории по датам: тренировки/частота, вес и талия старт→финиш с темпом, ПР за период,
  дисциплина. `coach_costs` — помесячные расходы токенов по журналам генераций.
### 8.8. Лента «Истории»: события и подсказки в разрывах

Лента — один список из трёх видов записей: тренировки, события и подсказки в разрывах.
Порядок — по дате убыванием; на общей дате тренировка стоит выше события, событие выше
подсказки, а порядок нескольких тренировок одного дня остаётся тем, который задала
сортировка §7.1.

**Разрыв** — сплошной ряд дней без тренировок между двумя соседними тренировками; верхний
разрыв считается от последней тренировки до сегодняшнего дня включительно. Подсказка
«N дн. без тренировок · отметить событие» показывается, если разрыв не короче трёх дней и
его не перекрывает ни одно событие (открытое событие перекрывает всё до сегодня). Короче
трёх дней — это не перерыв, а обычный отдых: объяснять там нечего.

Подсказка — единственная точка входа в создание события, и это сознательно: свайп влево
занят удалением, свободных целей на экране нет. Побочный эффект и есть главное свойство —
интерфейс физически не может предложить событие на дату, где уже есть тренировка (правило
дня, §4.5). Подсказка из верхнего разрыва открывает композер с открытым концом («ещё
идёт»), подсказка между тренировками — с готовыми датами разрыва.

**Карточка события** — не бумага, а незалитый блок с пунктирной обводкой на той же рельсе
64 pt: в ленте это буквально дырка, на которой оставили подпись. Рельса показывает дату
(число или диапазон чисел; месяцев два, если период на стыке) и вместо длительности
тренировки — «N дн.» либо «идёт» с точкой-индикатором. Текст режется по четырём строкам,
целиком он виден в правке. У открытого события в карточке есть действие «Закончилось».

**Композер события** — шит с детентами: две даты (системный `DatePicker`, будущее
запрещено, конец не может уехать раньше начала), переключатель «Ещё идёт», счётчик дней,
пять пресетов (`Болезнь` · `Травма` · `Поездка` · `Не спал` · `Зал закрыт`) и поле текста.
Пресет подставляет текст, а не категорию: пустое поле и поле ровно с другим пресетом
заменяются целиком, написанное руками дополняется, повторный тап по выбранному очищает
поле — промах всегда обратим. Переключатель «Ещё идёт» недоступен, если открытое событие
уже есть и правим мы не его: иначе backend отказал бы уже на сохранении. В правке
появляется удаление; сохранение без текста невозможно. Отказ сервера (второе открытое
событие, будущая дата, нет связи) показывается строкой под полем, а не тостом: тост
рисуется под шитом, и на этом экране его не видно.

**Пустое состояние** «История пуста» показывается, только когда нет ни тренировок, ни
событий.

### 8.9. Открытое событие на «Сегодня» и пересчёт плана

Пока событие открыто, на «Сегодня» висит плашка «‹первая строка текста› · N дн.» с
подписью «План сегодня легче обычного» и действием «Закончилась?». Плашка — состояние, а
не упрёк: нейтральные чернила, без красного и без слова «пропущено». Она совместима с
начатой сессией и остаётся на месте, пока событие идёт; тап открывает правку. День начала
считается первым.

Создание, правка и удаление события **всегда** пересобирают рекомендацию — так же, как
новый замер, и независимо от дат события: backend ставит фоновую генерацию, клиент (если у
пользователя уже есть история тренировок) переходит на тот же pending-гейт. Следствие
принятое, а не побочное: пока идёт пересчёт, «Сегодня» прячет и план, и кнопку старта, то
есть запись события на 15–20 секунд гасит старт тренировки. Композер предупреждает об этом
строкой «Тренер перечитает план — как после нового замера».

Список событий клиент перечитывает молча: сегодняшняя тренировка закрывает открытое
событие на сервере без отдельного ответа об этом, и запись из чата с тренером (MCP) в
клиент тоже не стучится. При старте события едут внутри общего 3-секундного дедлайна
(§13.1) — они нужны первому же кадру «Истории» и «Сегодня».

### 8.10. Заметки: где вводятся

**Заметка к тренировке.** Обязательного шага в завершении сессии нет: после сохранения
новой тренировки поверх экрана появляется полоска «Тренировка записана» с итогом
(«N упр · N сет · N мин») и кнопкой «Заметка». Полоска живёт несколько секунд и уезжает
сама — её можно просто не заметить; тоста о сохранении при этом нет, чтобы два сообщения
об одном факте не перекрывали друг друга. Поздний вход — свайп «Заметка» на карточке в
«Истории» (§8.4). Сохранение заметки — это `PUT` всей тренировки (частичного апдейта у API
нет), поэтому клиент отправляет объект, полученный от сервера: в нём остаются и снапшот
плана, и `rir` подходов. Пустой текст удаляет заметку. Клиент при этом на pending-гейт не
переходит, а сервер, как и при любой другой правке тренировки, ставит фоновую
перегенерацию рекомендации (§8.7): заметка — контекст для следующей генерации, а не новый
факт о нагрузке.

**Заметка к подходу** вводится в шите быстрого ввода — том же, что открывается долгим
нажатием по «+» или тапом по summary-строке упражнения. Свёрнутая заметка — пунктирная
строка под кружками усилия, плюс кнопка-карандаш в шапке шита, по которой видно, есть
заметка или нет. Раскрытие переводит шит на полный детент: клавиатура иначе закрывает CTA.
Автофокуса нет намеренно, вместо него — «Готово» в тулбаре клавиатуры. Подход, добавленный
коротким тапом по «+», заметки не наследует; правка существующего подхода её сохраняет.

## 9. Конструктор новой тренировки

### 9.1. Вход в flow

Экран `New Workout` открывается из `Trainings` по FAB.

Если в `localStorage` уже есть живой черновик, пользователь попадает в него, а не в пустой flow.

### 9.2. Дата тренировки

Дата редактируется из компактного чипа в верхнем баре.

Отдельной большой карточки даты на экране нет.

### 9.3. Стартовое состояние

Если пользователь открывает `New Workout` без уже внесённых сетов, экран не должен быть пустым.

Вместо пустого состояния конструктор сразу показывает preview-карточки основных упражнений, как будто пользователь уже выбрал их из основной подборки, но ещё не добавил ни одного сета.

Остальные упражнения каталога доступны отдельно, через блок `Добавить упражнение`.

Правка уже записанной тренировки (§8.4) — исключение: экран показывает ровно её состав.
Ни preview-карточек основной шестёрки, ни упражнений сегодняшнего плана, ни заметки тренера
под упражнением: план и заметка — про сегодня, а правят прошлое, и подписывать ими чужую
сессию нельзя. Дописать упражнение, которого в тренировке не было, по-прежнему можно —
через `Добавить упражнение`, где доступен весь каталог (§9.5).

### 9.4. Как формируется основная подборка

Основная шестёрка строится по реальной истории тренировок пользователя:

- приоритет получают часто встречающиеся упражнения;
- дополнительно учитывается их типичная позиция внутри тренировки;
- целевой размер основной подборки — до 6 упражнений;
- `Жим гор.` всегда остаётся вне основной шестёрки (это дубль `Жим в тренажере`).

### 9.5. Preview-карточки и каталог «Добавить упражнение»

- упражнение не должно дублироваться в текущем черновике;
- preview-карточка показывает подсказки и кнопку planned add, но не считается начатым упражнением, пока не появился реальный сет;
- после первого сохранённого сета preview-карточка превращается в обычную draft-карточку;
- если пользователь открыл set-modal, но закрыл его без сохранения первого сета, пустая карточка не должна остаться в черновике;
- `Добавить упражнение` открывает каталог и не должен пополнять основную шестёрку;
- каталог содержит **все** упражнения справочника, которых сейчас нет карточкой на экране, — от самого частого в истории к самому редкому. Отсечение считается от показанных карточек, а не от основной шестёрки: карточки задаёт то план тренера, то шестёрка, и упражнение вне плана иначе пропадало бы отовсюду — ни карточки с `+`, ни строчки в каталоге;
- пустой каталог (`Все упражнения уже на экране`) означает ровно это и возможен только когда карточками показан весь справочник;
- когда все упражнения основной шестёрки реально начаты, показывается completion-state `Круто, тренировка закончена`, но каталог остаётся доступным.

### 9.6. Суперсеты

Конструктор поддерживает параллельное ведение нескольких упражнений:

- не нужно “заканчивать” одно упражнение, чтобы начать второе;
- пользователь может чередовать сеты между карточками;
- у каждой карточки своё текущее состояние, собственный planned add и своя история progress/reference.

### 9.7. Единый источник плановой логики

План по упражнению должен считаться в одном месте и переиспользоваться везде одинаково.

Один и тот же helper обязан обслуживать:

- reference-строку в карточке упражнения;
- reference-строку в set-modal;
- быстрый planned add по синему `+`;
- стартовые значения ручного set-modal;
- кольцевой прогресс вокруг FAB;
- потенциальный возврат UI `next workout plan`, если фича снова будет включена.

### 9.8. Карточка упражнения в конструкторе

Карточка упражнения содержит:

- заголовок с названием и маленькой пиктограммой упражнения;
- reference-строку `прошлое выполнение → план`;
- компактную синюю строку уже внесённых сетов;
- один большой синий `+` справа.

Summary уже внесённых сетов использует ту же логику схлопывания, что и история тренировок.

Если синяя строка умещается в одну линию, она должна оставаться одной строкой. Если не умещается, она может аккуратно перейти на две строки.

### 9.9. Формат reference-строки

Reference-строка строится из двух частей:

- серая часть — прошлое выполнение;
- зелёная часть — planned target на текущую тренировку.

Важно:

- смайлики `effort` относятся только к прошлому выполнению;
- в плановую зелёную часть они не копируются;
- строка должна стараться оставаться в одну линию;
- если не помещается, допускается перенос на две строки без визуального развала по вертикали.

### 9.10. Быстрое добавление planned set

Короткий тап по синему `+` не открывает модалку, а сразу добавляет следующий planned set.

Правила:

- источник плана — последнее подходящее выполнение упражнения;
- очередность идёт по порядку прошлых сетов;
- в каждый planned set добавляется `+1` к повторам;
- `effort` из прошлого выполнения не копируется в planned set;
- если в истории по упражнению ничего нет, fallback остаётся простым: используется последний известный вес и `12` повторений.

### 9.11. Ручной ввод сета по long press

Long press по синему `+` открывает ручной set-modal.

Ручной ввод не должен открываться по случайному тапу в любую область карточки. Только по long press на самой кнопке `+`.

### 9.12. Set-modal

Актуальная модалка сета устроена так:

- закрывается тапом вне модалки;
- отдельной кнопки `Отмена` нет;
- отдельного заголовка `Новый сет` / `Редактировать сет` нет;
- сверху показывается название упражнения с иконкой и reference-строка;
- ниже идут две компактные stepper-строки:
  - вес в формате `120,5 кг`;
  - повторы в формате `11 ПТ`;
- stepper-кнопки используют тот же общий синий круглый стиль, что и `+` на карточке упражнения;
- внутри модалки можно выбрать `effort` через `🙂 / 😐 / 😣`;
- основное действие модалки только одно: `Применить`.

### 9.13. Long press по карточке упражнения

Long press по поверхности карточки упражнения открывает центрированную modal-карточку в том же визуальном паттерне, что и set-modal.

В ней доступны два действия:

- удалить последний сет;
- удалить всё упражнение.

Отдельный draft-swipe для удаления больше не является частью актуального UX.

### 9.14. FAB-ы внутри конструктора

Пока в черновике нет ни одного реального сета, FAB-ы не показываются.

После появления первого сета становятся видны:

- чёрный save-FAB справа;
- красный reset-FAB слева.

### 9.15. Reset-flow

Красная кнопка не сбрасывает черновик мгновенно.

Она сначала показывает confirm, и только после подтверждения:

- очищает черновик;
- возвращает экран в исходное состояние.

### 9.16. Кольцевой прогресс вокруг FAB

Save-FAB и FAB на `Trainings` могут быть окружены кольцевым прогрессом.

Правила:

- прогресс считается только по упражнениям основной шестёрки;
- вклад упражнения зависит от доли выполненных planned sets относительно плана этого упражнения;
- простое открытие модалки без применения сета прогресс не увеличивает;
- быстрое planned add и ручное сохранение сета увеличивают прогресс одинаково через общую плановую логику;
- при удалении сетов или упражнения прогресс должен убывать симметрично;
- кольцо анимируется вперёд и назад при изменении состояния черновика.

### 9.17. Автоскролл конструктора

Если пользователь добавляет новое упражнение и его карточка оказывается вне видимой области, экран должен подскроллиться так, чтобы новая карточка оставалась выше нижних FAB-ов.

### 9.18. Сохранение тренировки

При сохранении:

- frontend отправляет тренировку на backend;
- backend нормализует payload;
- тренировка получает серверный `id`;
- черновик очищается;
- новая запись сразу появляется в `Trainings`, `Progress` и влияет на будущий planned add.

Save-FAB должен показывать явное loading-состояние, а не выглядеть как зависший UI.

### 9.19. `load_type`: только честный источник

`load_type` тренировки берётся из применённого плана тренера (iOS передаёт
`load_type` рекомендации при сохранении тренировки по плану). Если тренировка шла
без плана, поле хранится как `null` и в коуч-промпте показывается как `[без плана]` — так
модель не читает его как пробел в данных.

Старая эвристика «вывести load_type из суммарного тоннажа» (>=3000 → heavy) удалена:
она помечала heavy практически любую реальную сессию, и на этой сломанной метке
держалось жёсткое правило «после heavy не heavy» — из-за чего модель фактически не
могла запланировать heavy-день. Реальную тяжесть сессии коуч-модель оценивает сама
по весам и повторам; фальшивый лейбл хуже честного «неизвестно».

В текущем UX это серверное поле сохраняется, но не обязано быть визуально видимым на истории тренировок.

### 9.20. Голосовая запись подхода (Siri)

Подход можно записать голосом, не доставая телефон. Рабочая форма — телеграфная:
«Зал жим ногами» засчитывает подход по плану одной фразой, «Зал подход» →
«жим ногами 80 на 10, тяжело» пишет произвольный. По-английски то же через
кодовое слово `Gym`. Команда выполняется в процессе приложения
(система поднимает его в фоне), не разблокирует экран и не выводит приложение на
передний план. Полная спецификация — в
[ios/VOICE_LOGGING_BRIEF.md](./ios/VOICE_LOGGING_BRIEF.md).

Продуктовые правила, которые голос обязан соблюдать:

- голос не создаёт нового хранилища: подход попадает в тот же черновик, что и
  подход из UI, и отправляется на backend тем же явным шагом;
- тренировка начинается первым реальным сетом — как и в конструкторе;
- не названные вес и повторы берутся из того же единого источника плановой
  логики, что и синяя кнопка `+` (см. §9.7);
- незакрытый черновик за другой день не пополняется и не стирается молча:
  команда отклоняется с просьбой открыть приложение. Сессия, перешедшая за
  полночь, продолжается — черновик живой, пока последнему сету меньше 6 часов;
- нераспознанное или неоднозначное упражнение переспрашивается, а не угадывается:
  записать подход не в то упражнение хуже, чем переспросить;
- ответ всегда проговаривает записанное — это единственная защита от ошибки
  распознавания; аномальный вес (расхождение с планом в 2.5 раза) называется явно;
- вес и повторы клампятся в 0…500 кг и 1…100 повторов;
- отмена последнего подхода доступна голосом и целится в последний добавленный
  сет независимо от способа добавления;
- русская и английская Siri поддержаны одинаково, и отвечать надо на языке
  вопроса: язык телефона и язык Siri в iOS настраиваются независимо, поэтому
  язык определяется по самой произнесённой фразе;
- вес, названный в фунтах, пересчитывается в килограммы: приложение хранит
  только килограммы, и записать «80» вместо «80 pounds» значит тихо испортить
  историю;
- фраза обязана быть короткой: между подходами человек не произносит
  предложение. Отсюда телеграфный регистр у каждой команды — имя приложения
  в фразе обязательно по правилам Siri, поэтому оно сделано односложным
  кодовым словом.

## 10. Экран Progress

### 10.1. Назначение

Экран отвечает на два вопроса:

- сколько тренировок было в выбранном диапазоне;
- как растут рабочий вес и повторения по конкретному упражнению.

### 10.2. Диапазоны

Доступны:

- `7D`
- `30D`
- `All`

### 10.3. Summary

В summary сейчас показывается только:

- количество тренировок за период.

Старые объёмные метрики вроде `Volume`, `Top Exercise`, `Heaviest Set` и `Average Volume` не считаются частью актуального продукта.

### 10.4. Выбор упражнения

Селектор строится из реальной серверной истории пользователя.

Каталог упражнений может использоваться как fallback, но основной смысл экрана — анализ уже реально встречавшихся упражнений.

### 10.5. Серии на графике

Для каждой тренировки в выбранном диапазоне строятся две линии:

- `Вес` — самый тяжёлый сет упражнения на тренировке;
- `Повторы` — сет с максимумом повторений на тренировке.

### 10.6. Snapshot-карточки

Под выбранное упражнение показываются три snapshot-карточки:

- `Старт`
- `Сейчас`
- `Изменение`

Они отражают первый и последний points текущего диапазона.

## 11. Экран Weight

### 11.1. Назначение

Экран отвечает за контроль веса тела.

### 11.2. Основные элементы

Экран содержит:

- диапазоны `7D / 30D / All`;
- компактный inline composer;
- summary-strip;
- график веса тела.

### 11.3. Inline composer

Composer состоит из:

- чипа с датой;
- поля ввода веса;
- кнопки сохранения.

Надзаголовков и лишних поясняющих текстов в актуальном UI нет.

### 11.4. Правило сохранения веса

На одну дату у пользователя существует только одна запись.

Поэтому повторное сохранение на ту же дату:

- не создаёт дубль;
- обновляет уже существующее значение.

### 11.5. Summary-strip

На экране показываются три компактные метрики:

- `Последний`
- `Дельта`
- `Записей`

### 11.6. График веса тела

График показывает:

- только реальные записи пользователя;
- по оси `Y` — только реально введённые значения веса, без искусственных промежуточных меток;
- по оси `X` — даты текущего диапазона данных.

### 11.7. Удаление записи веса

Тап по точке графика открывает confirm на удаление записи.

При подтверждении:

- запись удаляется на backend;
- график и summary сразу пересчитываются.

## 12. Правила отображения чисел

### 12.1. Рабочие веса в тренировках

Вес отображается компактно, без пробела перед `кг`.

Примеры:

- `60кг ×14`
- `60кг ×14×3`

### 12.2. Повторы

Повторы отображаются целыми числами.

### 12.3. Вес тела

Для веса тела UI не должен навязывать искусственное округление осей до одной цифры после запятой, если пользователь вводил более точное значение.

## 13. Загрузка и ошибки

### 13.1. Старт приложения

На старте приложение:

1. инициализирует Telegram shell, если он доступен;
2. пытается вызвать `disableVerticalSwipes()` и `requestFullscreen()`, если клиент это поддерживает;
3. восстанавливает черновик и UI-состояние;
4. резолвит пользовательскую сессию;
5. одним параллельным заходом под общим 3-секундным дедлайном загружает справочник
   упражнений, тренировки, вес тела, замеры талии и события;
6. строит итоговое состояние.

### 13.2. Loading-screen

Во время старта показывается отдельный branded loading-screen.

### 13.3. Ошибка загрузки

Если boot не собрался, показывается экран ошибки с возможностью повторить загрузку.

## 14. Инварианты для тестов

### 14.1. Пользовательские данные

- данные одного пользователя не должны попадать в контекст другого;
- Telegram-shell не должен “залипать” на debug-user;
- recovery и fallback должны быть предсказуемыми и покрыты тестами.

### 14.2. Trainings

- список всегда берётся с backend;
- карточки отсортированы по правилу свежести;
- swipe edit/delete работают;
- summary сетов компактно группируется;
- новая тренировка сразу появляется в истории;
- load-badge не должен случайно вернуться в текущий UX, пока продуктово он выключен;
- лента склеивает тренировки, события и подсказки в разрывах одним списком по дате;
- подсказка о событии не может попасть на дату, где уже есть тренировка; перерыв короче
  трёх дней молчит; разрыв, перекрытый событием, подсказки не даёт;
- открытое событие считается длящимся до сегодняшнего дня, и день начала считается первым;
- «ещё идёт» уезжает на сервер явным `null` в `end_date`, а не пропущенным ключом:
  пропущенный ключ на `PUT` не снял бы уже проставленный конец;
- сохранение заметки к тренировке не теряет `rir` подходов — `PUT` уезжает объектом целиком;
- заметки видны в карточке истории: введённый текст должен быть перечитываем.

### 14.3. New Workout

- FAB-ы не появляются до первого реального сета;
- стартовый экран конструктора должен сразу показывать preview-карточки основной шестёрки, а не пустую плитку;
- пустое выбранное упражнение не должно сохраняться после закрытия модалки без применения первого сета;
- короткий тап по синему `+` должен добавлять следующий planned set, а long press по нему открывать ручной modal-flow;
- выбранный `effort` должен сохраняться в set и отображаться в текущем draft и в истории тренировок;
- summary введённых сетов в draft-карточке должно использовать ту же логику схлопывания, что и история тренировок;
- tap по синей summary-строке должен редактировать именно последний сет упражнения;
- long press по карточке упражнения должен открывать центрированную modal-карточку удаления;
- completion-state основной подборки должен появляться только после реального исчерпания упражнений основной шестёрки;
- `Добавить упражнение` должно предлагать любое упражнение справочника, которого нет на экране, — в том числе при применённом плане тренера, где карточки задаёт план, а не основная шестёрка;
- правка записанной тренировки должна показывать ровно её состав: ни preview-карточек основной шестёрки, ни упражнений и заметок сегодняшнего плана;
- автоскролл должен удерживать новые карточки выше FAB-ов;
- прогресс-кольцо должно расти и убывать пропорционально выполненным planned sets, а не просто по наличию любого сета;
- при возвращении к живому черновику пользователь попадает в него, а не в новый пустой flow.

### 14.3.1. Голосовая запись подхода

- фраза разбирается независимо от порядка слов, формы единиц и того, записало ли
  распознавание числа цифрами или прописью;
- пары-ловушки каталога («сгибания» / «разгибания», «бицепс» / «бицепс бедра») не
  должны путаться;
- неоднозначная фраза («тяга 55 на 12») обязана вернуть кандидатов, а не выбрать
  одного из них;
- непонятая фраза не должна начинать тренировку;
- черновик за другой день не должен пополняться голосом, а сессия через полночь —
  должна продолжаться в том же черновике;
- отмена должна снимать именно последний добавленный сет, в том числе при
  суперсетах;
- «что дальше» не должно ничего записывать;
- ответ Siri должен содержать записанные вес и повторы;
- ответ должен быть на языке произнесённой фразы, а команда без фразы —
  на языке последней распознанной;
- фразы Siri должны собираться для обеих локалей: в логе шага
  `AppIntentsSSUTraining` обязаны быть и `for ru`, и `for en`.

### 14.4. Progress

- число тренировок в summary равно числу тренировок в выбранном диапазоне;
- для выбранного упражнения линии строятся по лучшему весу и лучшим повторам на тренировку;
- если данных нет, экран должен показывать понятное пустое состояние.

### 14.5. Weight

- запись на ту же дату должна обновляться, а не дублироваться;
- график должен строиться по реальным данным пользователя;
- удаление по тапу на точку должно реально удалять запись на backend.

## 15. Текущие ограничения

- эвристический `Плана следующей тренировки` отключён в UI (код сохранён); вместо него работает LLM-«Совет тренера» (см. §8.7);
- авторизации как таковой нет: iOS работает в personal-build режиме с фиксированным `native_user_id`, браузер — в debug-режиме;
- одна запись веса тела на дату — это текущая продуктовая модель, а не история нескольких измерений за день;
- `focus` тренировки пользователем не вводится — он приходит из применённого плана; свободная заметка ко всей сессии вводится, см. §8.10;
- `effort` задаётся тремя дискретными состояниями; свободный комментарий у подхода теперь есть, а `rir` из приложения по-прежнему не вводится — клиент только сохраняет уже записанное значение;
- будущие события (отпуск с 1 сентября) не поддерживаются: backend отклоняет будущие даты с обоих концов, планирование отложено;
