# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

`Pocket Coach` (приложение `Trainer`) — карманный ИИ-тренер по силовым: нативный iOS-клиент
(SwiftUI) + self-hosted backend на SQLite + MCP-сервер для разговора с данными. Продукт
**personal-build**: один захардкоженный пользователь (`id=3`), без публичной авторизации.
Веб-мини-апп и Telegram-бот удалены в июне 2026, их остатки с VPS вычищены в сентябре — если
встретишь следы (`web/`, `bot.py`, `MINIAPP_TELEGRAM_*`, `MINIAPP_STATIC_DIR`), это легаси, не
восстанавливай.

Рабочий язык репозитория — русский: документация, тексты продукта, комментарии к
нетривиальным решениям. Заголовки коммитов — английские, в императиве
(`Coach: sharpen the return-from-break policy block`).

## Команды

Всё запускается из корня репозитория. Backend — **чистый stdlib Python**, без зависимостей и без
venv; единственный компонент с pip-зависимостями — `coach_mcp/`. **На VPS системный Python 3.10**,
локально 3.13: CI гоняет suite на обеих, а `target-version = "py310"` в `ruff.toml` держит pyupgrade
от подсказок в сторону 3.11+ (`datetime.UTC`, `tomllib`, `StrEnum`, вложенные кавычки в f-строках,
`date.fromisoformat`, который там принимает и `20260801`: даты с клиента гейтит регулярка в
`rules._parse_input_date`).
Ничего из этого в `backend/` и `coach_mcp/` не использовать, пока VPS не обновлён; тогда поднять и
матрицу, и target-version.

```bash
# backend локально (http://127.0.0.1:8080)
MINIAPP_ALLOW_DEBUG_USER=1 python3 backend/server.py

# весь тестовый suite (то же, что гоняет CI)
python3 -m unittest discover -s backend/tests -p "test_*.py" -v

# один файл тестов
python3 -m unittest discover -s backend/tests -p "test_coach_signals.py" -v

# один класс или метод (-k фильтрует по имени)
python3 -m unittest discover -s backend/tests -p "test_coach_signals.py" -k WaistLimitSignalTests -v
```

`python3 -m unittest backend.tests.test_x` **не работает**: `tests/support.py` сам вставляет
`backend/` в `sys.path` при импорте, поэтому тесты запускаются только через `discover -s backend/tests`
(либо `PYTHONPATH=backend:backend/tests python3 -m unittest test_x.Class.method`).

iOS (из `ios/`):

```bash
xcodebuild -project TrainerIOS.xcodeproj -scheme TrainerIOS -destination 'generic/platform=iOS Simulator' build
xcodebuild -project TrainerIOS.xcodeproj -scheme TrainerIOS -destination 'platform=iOS Simulator,name=iPhone 17' test
```

Линтеры и форматтеры (конфиги в корне — `ruff.toml` и `.swift-format`):

```bash
ruff check .            # Python: линт          (brew install ruff)
ruff format .           # Python: формат
pyright                 # Python: типы          (brew install pyright или pip install pyright)
git ls-files -z '*.swift' | xargs -0 xcrun swift-format lint --strict --parallel
git ls-files -z '*.swift' | xargs -0 xcrun swift-format format --in-place --parallel
shellcheck backend/infra/deploy/deploy.sh .claude/hooks/claude-md-reminder.sh
actionlint              # .github/workflows/*.yml (brew install actionlint)
```

`swift-format` ставить не надо — он идёт в тулчейне Xcode, `xcrun` находит его сам.
**Версия ruff закреплена в двух местах**: строка `pip install ruff==X` в `ci.yml` и упоминание
в шапке `ruff.toml`. Новый ruff умеет находить новые замечания, поэтому его подъём — отдельный
осознанный коммит, а не сюрприз на чужом PR.

**pyright — второй гейт по Python, конфиг в `pyrightconfig.json`.** Режим `standard`, `pythonVersion`
там 3.10 по той же причине, что `target-version` в ruff: обращение к API стандартной библиотеки из 3.11+
должно падать в CI, а не на VPS. Версия закреплена строкой `pip install pyright==X` в `ci.yml`. Для
`coach_mcp` в CI ставятся его зависимости, чтобы типы `mcp` разрешались; локально нужен тот же venv.
Функции, которые возвращают `None` «когда нечего вернуть», в тестах сужаются через `assert x is not None`
(в `ruff.toml` для тестов выключен `S101`), а не через `assertIsNotNone`: второй pyright не понимает.

Два порога длины строки не совпадают намеренно: форматтер укладывает **код** в 100 символов сам,
а `E501` включается только со 120 — это ловушка для того, что форматтер разбить не может
(семантика каталога в `prompt_builder.py`, описания MCP-инструментов, SQL). Рвать такие тексты
руками ровно по сотне вредно: их читают модель и человек.

Автоматических гейта четыре: `lint` (всегда, ubuntu — ruff + pyright + shellcheck + actionlint),
unittest-suite (всегда), `swift-format lint --strict` и iOS-тесты (оба в macOS-джобе, только
когда тронут `ios/`). Swift-линт стоит **до** тестов: он занимает секунды, и незачем держать
дорогой macOS-раннер 15 минут, если человек просто забыл прогнать форматтер. Имя симулятора
в воркфлоу не захардкожено — берётся последний доступный iPhone, иначе смена образа раннера
уронила бы сборку без причины.

`ruff.toml` держит несколько отключений, и каждое — решение, а не умолчание: `RUF001-003`
(рабочий язык русский, кириллические `с`/`а`/`е` для линтера «неоднозначны» — 330+ ложных
замечаний), `DTZ011` (тренировочный день — локальный день атлета, не UTC) и правила про
неиспользуемые аргументы в `backend/tests/*` (фейки обязаны повторять сигнатуру настоящих
функций). Прежде чем глушить новое правило, дописывай туда же почему.

`BLE` (blind-except), наоборот, включён специально: в коде уже стояли 23 пометки
`# noqa: BLE001` — ровно по числу мест с `except Exception`. Правило было нужно автору,
просто не было включено; без него пометки превращаются в мусор, ruff их сносит, а новый
blind-except проезжает молча.

Деплой: пуш в `main` → CI прогоняет тесты → если затронут backend, деплоит его на VPS.
Ручной вариант — `./backend/infra/deploy/deploy.sh backend`; другие цели — `coach-mcp`, `proxy`
(Caddyfile обратного прокси, CI его не деплоит) и `all`.

## Архитектура

### Три процесса, одна база

```
iOS (SwiftUI)  ──HTTP+cookie──►  backend/server.py  ──►  SQLite (trainer.db)
                                                            ▲
Claude Desktop ──MCP──►  coach_mcp/server.py  ──────────────┘
                          (импортирует backend/*.py напрямую)
```

`coach_mcp` — не отдельный сервис поверх API, а **второй процесс поверх той же базы**: он
импортирует `backend_store` / `recommender` / `coach_features` / `coach_state` и видит ровно то же,
что генерирует backend. Поэтому изменение сигнатуры в `backend/trainer/` может молча сломать MCP.
Через MCP не только читают: талию и события (`coach_list_events` / `coach_add_event` /
`coach_update_event` / `coach_delete_event`) записывают прямо из разговора с тренером — это
штатный сценарий, а не отладка. У событий два равноправных клиента, iOS и Claude Desktop,
поэтому правила модели (запрет будущего, одно открытое событие) живут в `domain/rules.py`,
а не в хендлерах и не в UI.

Раскладка `backend/`: наверху то, что читают глазами, — код, проза и тесты; обвязка сложена в
две папки. Имена модулей внутри те же, что и раньше, поэтому в документации они упоминаются по
имени файла (`coach_state.py` значит `backend/trainer/domain/coach_state.py`).

```
backend/
├── server.py      HTTP API — процесс, который крутит systemd; импортирует всё остальное
├── trainer/       пакет из двух частей: domain/ — правила и методика (см. ниже),
│                  data/ — backend_store (SQLite), files (состояние, профиль, стратегия,
│                  каталог), coach_prompts (шаблоны), anthropic_client (HTTP к Claude),
│                  parsing (разбор значений с провода: тип, границы, текст ошибки),
│                  rule_engine (правила плана как текст: разбор, выражения, ход проверки)
├── prompts/       проза для модели
├── tests/
├── infra/         deploy/ (deploy.sh и systemd-юниты) и jobs/ (скрипты таймеров)
└── resources/     exercises.json (каталог упражнений), signals.md (тексты баннеров) и
                   plan_notes.md (пометки валидатора в rationale) — читает клиент, не модель
```

Импорт — `from trainer.domain import coach_state`, `from trainer.data import backend_store`; где лежат `prompts/`, `resources/` и локальная
`data/`, модули узнают через `trainer.BACKEND_DIR`. Скрипты в `infra/jobs/` запускаются как файлы
(`python3 backend/infra/jobs/weekly_report.py`), поэтому корень backend в `sys.path` кладут сами.
`__init__.py` есть только у `trainer/` — там живёт `BACKEND_DIR`; `domain/`, `data/`, `infra/` и
`coach_mcp/` импортируются как namespace-пакеты без него, и новой подпапке этот файл не нужен.

`server.py` — `BaseHTTPRequestHandler` без фреймворка: `do_*` отдают запрос в `_dispatch`, а тот
ищет обработчик в таблицах `ROUTES` (метод + точный путь) и `ID_ROUTES` (`/api/<коллекция>/<id>`).
Один эндпоинт — один метод `_get_*` / `_post_*` / `_put_*` / `_delete_*`; новый эндпоинт — это
метод плюс строка в таблице. Сессию обработчик берёт через `_require_user`, который сам отвечает
401. Вся нормализация и валидация входа живёт в `domain/rules.py` (`normalize_*`), не в хендлерах и
не в SQL; механика разбора отдельных значений — в `data/parsing.py`.

### Слой коуча — где проходит граница «алгоритм / LLM»

Это главный инвариант проекта. **LLM вызывается ровно в двух местах**, оба в `recommender.py`:
план следующей тренировки и недельный отчёт. Всё остальное детерминировано. Модули ниже лежат в
`backend/trainer/domain/`, кроме `coach_prompts.py`, `anthropic_client.py`, `parsing.py` и
`rule_engine.py` — они в `data/`.

```
SQLite: workouts, body_weights, waists, events + coach_state.json + coach_profile.json
   │
   ├─ limits.py         ГРАНИЦЫ ДОПУСТИМОГО: метки, диапазоны и потолки для входа с клиента,
   │                    ответа модели и аналитики, каждое число с объяснением. Порогов
   │                    методики (свежесть замеров, частота deload, недели застоя) здесь
   │                    нет: они лежат у своей логики и описаны в docs/
   │
   ├─ rules.py          форма входа по границам из limits (тренировка, замеры, события,
   │                    снапшот совета, план от модели, даты) и решения при записи: что сохранить при ретрае и правке,
   │                    одно открытое событие, сегодняшняя тренировка закрывает его вчерашним
   │                    днём. Стор и хендлер пишут то, что вернули отсюда, сами не решают.
   │
   ├─ parsing.py        (в data/) механика разбора под rules: `as_int` / `as_float` /
   │                    `as_date` / `as_text` / `as_choice` и их сообщения об ошибке. Про
   │                    тренировки и замеры не знает ничего, поэтому это трубопровод, а не
   │                    домен; нужен, чтобы в rules остались только границы и решения.
   │
   ├─ coach_state.py    фаза (cut_recomp / lean_bulk / maintenance), неделя блока,
   │                    ramp недельного объёма, плановый deload, «возврат после перерыва» (≥14 дней)
   │
   ├─ coach_features.py вычисляемые фичи вместо сырой истории: e1RM по Эпли, ПР, % от пика,
   │                    позиция упражнения в сессии, эффективные недельные объёмы, явка по
   │                    календарным неделям, детектор застоя по АКТИВНОМУ окну блока (от
   │                    старта фазы/возврата, отпуск в окно не входит), ступени возврата к
   │                    доперерывному рабочему (не к пику), тренды веса/талии, матрица
   │                    питания по коридору темпа фазы, дисциплина «факт vs план»
   │
   ├─ resources/signals.md  ТЕКСТЫ БАННЕРОВ для клиента — не промпт, модель их не видит.
   │                    Пороги и жизненный цикл остаются в coach_signals.py: ключ
   │                    эпизода строится из фактов, поэтому правка текста не трогает
   │                    ни схлопывание, ни дисмиссы. Рядом plan_notes.md — пометки
   │                    «Проверка методики», которые валидатор дописывает в rationale.
   │
   ├─ prompts/*.md      ВСЯ ПРОЗА, которую читает модель: system, phase_policy, report
   │                    (шаблоны целиком), user_blocks (подписи к блокам, «## имя») и
   │                    plan_rules (жёсткие границы плана целиком: формулировка для
   │                    системного промпта и «для / требует / нарушение / починить»
   │                    для сервера — исполняется тот же блок, который читает модель).
   │                    Слоты `{{name}}`, загрузчик coach_prompts.py — он ничего не
   │                    решает и не считает. Правка методики — это диф текста, а не
   │                    перемешанных кавычек. В prompt_builder.py прозы не осталось.
   │
   ├─ prompt_builder.py Всё, что читает модель, собирается здесь: системный промпт (профиль
   │                    атлета + семантика каталога + политика фаз — АКТИВНАЯ фаза рендерится
   │                    из phase_params атлета, чтобы политика и КОНТЕКСТ не расходились
   │                    числами + срез стратегии) + user-промпт (контекст + фичи + сырые
   │                    ~10 тренировок вперемешку с событиями) + JSON-схема ответа +
   │                    промпт недельного отчёта. Считает слоты, прозы не содержит.
   │
   ├─ recommender.py    Точка входа и ОБА вызова модели: план и недельный отчёт. Загружает
   │                    каталог, профиль и стратегию, собирает промпт → structured output
   │                    по JSON-схеме → валидатор → один авто-репромпт → детерминированное
   │                    разрешение. Генерация не падает из-за методики. Здесь же жизненный
   │                    цикл совета: когда он stale, какая правка данных его обесценивает,
   │                    когда таймер обязан пересобрать его и когда пишется недельный отчёт.
   │
   ├─ plan_validator.py Правил здесь нет — они текст в prompts/plan_rules.md. Здесь
   │                    Bounds (факты истории, посчитанные до вызова модели) и словарь,
   │                    которым правила написаны: SCOPES (по чему идти и что при этом
   │                    известно) и PROCEDURES (как чинить). Книгу собирает и исполняет
   │                    data/rule_engine; violations — строки для репромпта, resolve —
   │                    починка после второго промаха с пометкой в rationale.
   │                    Санитизация ответа — rules.normalize_model_plan, не здесь.
   │
   ├─ anthropic_client.py  HTTP к Claude API на stdlib urllib: ретраи на временные сбои,
   │                    prompt caching, structured output. Ни тренировок, ни промптов не
   │                    знает; единственное место, где открывается соединение с API.
   │
   └─ coach_signals.py  БАННЕРЫ БЕЗ LLM. Пороги + шаблоны текста + схлопывание семейств.
                        Одинаковые данные всегда дают одинаковый список. Решение по дисмиссу
                        (критический не откладывается, сроки по severity) тоже здесь.
```

**Свободный текст атлета — отдельный вход в промпт, и единственный, который мы не считаем.**
Заметка к подходу, заметка к сессии и события (таблица `events` — периоды без тренировок с
причиной) уезжают в модель дословно и больше нигде не участвуют: ни фичи в
`coach_features.py`, ни сигнала, ни проверки в валидаторе из них не появилось. Методика
«после болезни возвращайся как после перерыва, даже если дней меньше 14» — фраза в
`prompts/system.md`, а не порог в `coach_state.py`. Окна по датам у хроники событий нет
намеренно (событие любой давности всё ещё объясняет дырку в датах), поэтому единственная
страховка от растущего промпта — потолок `MAX_EVENT_LINES` в `prompt_builder.py`, и обрезка
объявляется в самом промпте отдельным блоком. Канал включается на стороне вызывающего:
`events=` — необязательный аргумент `prompt_builder._build_user_prompt` / `generate` / `generate_with_trace`,
и не переданный он молча выключает и хронику, и открытое событие. Промпт при этом собирается
без единой ошибки, а тесты промпта передают `events=` сами — поэтому каждый живой вызыватель
проверяется отдельно (`EventsReachGenerationTests` в `backend/tests/test_events_and_notes.py`:
`server.py`, `refresh_recommendation.py`, `weekly_report.py`). У четырёх мест в `coach_mcp`
теста нет — там проверка глазами, в `coach_preview_prompt`.

**Валидатор проверяет ровно три жёсткие границы** (блоки с «требует:» в `prompts/plan_rules.md`): покрытие групп
(крупная группа или бицепс бедра, сухие ≥10 дней, обязаны попасть в план), возвратный потолок
весов (после перерыва вес не выше доперерывного рабочего) и потолок размера сессии (верхняя
граница `session_sets` фазы; при повторном промахе сервер сам режет подходы с хвоста плана и
пишет об этом в rationale). Диапазоны повторов, нижняя граница сессии, шаги весов, чередование
heavy/medium/light — **сознательно не проверяются**, это суждение модели, направляемое промптом.
`rest_days` клампится 0–4 молча. Не добавляй новых проверок в валидатор без явной просьбы:
несколько коммитов подряд убирали методику из кода в промпт; потолок сессии добавлен по разбору
сентября 2026 — карточки на 19–22 подхода при коридоре 10–20 срывали ~60-минутные сессии.
Правила — текст: блок в `prompts/plan_rules.md` несёт формулировку для системного промпта и
четыре ключа для сервера («для», «требует», «нарушение», «починить»); исполняет их
`data/rule_engine.py`, а слова («сухая группа», «тяжесть», «срезать подходы с хвоста до
потолка») объявлены словарём `SCOPES` / `PROCEDURES` в `plan_validator.py`. Слово не из словаря,
имя не из области, выражение вне грамматики, слот без значения или пометка без починки
останавливают сервер на старте, не на генерации; единственное, что проверяется по факту, —
что область даёт все имена, которые обещала в `provides`, и это ловится на первом же случае
(все три области прогоняются тестами). Новая проверка — это новый блок в markdown и слово в
словаре, если правило говорит о факте, которого сервер ещё не считает; `RulesTableTests`
пинит три имени, чтобы блок не появился незамеченным.

Кэш рекомендации — **одна перезаписываемая строка** на пользователя в `recommendations`
(`none`/`pending`/`ready`/`failed`); полная история генераций с токенами — append-only
`recommendation_log`. Поэтому в тренировку пишется **снапшот** совета (`data.recommendation`),
а не ссылка: только копия стабильна для статистики «факт vs план».

### iOS: четыре слоя + голосовой

- `TrainerLogic.swift` — **чистые статические функции** (сортировки, planned sets, summary,
  прогресс, объёмы). Ничего не знает про сеть и состояние; на нём висит основная масса тестов.
- `TrainerStore.swift` — `@MainActor ObservableObject`, единственный источник состояния,
  persistence черновика/настроек в `UserDefaults`, все мутации через API.
- `APIClient.swift` — HTTP. **Две URLSession намеренно**: дефолтная с таймаутом 3 с (чтобы
  сплэш не висел 60 с) и `longRunningSession` на 90 с только под `POST /api/recommendations/refresh`,
  который блокируется на генерации Claude.
- `Views/` — экраны и дизайн-система, файл на экран: `DesignSystem` (палитра, кнопки, фон,
  текстовые поля), `ExerciseGlyphs`, `SharedPieces`, `ContentView` (оболочка и вкладки),
  `CoachCard`, `TodayScreen`, `QuickAddSheet`, `SignalBanner`, `HistoryScreen`, `EventViews`,
  `WorkoutNoteSheet`, `ProgressScreen`, `ExerciseDetailScreen`, `MeasurementsScreen`,
  `SystemScreens` (настройки, вход, загрузка, ошибка, тост). Модуль один, поэтому экран,
  который показывает оболочка, объявлен internal, а не `private`.

Поверх них — **голосовой слой** (Siri / App Intents), тремя файлами в той же зависимости
«чистое → состояние → фреймворк»: `VoiceSetParser.swift` (язык и грамматика фразы, чистые
функции) → `TrainerStoreVoice.swift` (расширение стора: команды и тексты ответов) →
`VoiceIntents.swift` (App Intents и фразы Siri). Спека — [ios/VOICE_LOGGING_BRIEF.md](ios/VOICE_LOGGING_BRIEF.md).

Интенты объявлены **в таргете приложения, а не в расширении**: они выполняются в его процессе
(система поднимает его в фоне ради одной фразы) и работают с тем же `TrainerStore.shared`, что и
UI. Отсюда два следствия: стор стал синглтоном, а голосовой путь обязан работать без `boot()` —
каталог упражнений он берёт из бандла, если сети не было.

`reload()` ограничен дедлайном 3 с: не успели — рвём задачу и уходим в error screen с ретраем.
Рекомендация читается **вне** этого дедлайна, отдельным запросом после старта.

**Применённый план ≠ выполненные подходы.** «Применить в план» кладёт совет в
`TrainerStore.appliedPlan` (живёт в `UserDefaults`); тренировка не считается начатой, пока не
записан первый реальный сет. Приоритет следующего подхода по «+» един для всего конструктора:
последний кастомный подход повторяется → цель применённого плана по индексу → история +1 повтор
→ 12×0.

## Что легко сломать

**Проза промптов — в `backend/prompts/*.md`, а не в коде.** `coach_prompts.py` только грузит
шаблон и подставляет слоты `{{name}}`: он ничего не вычисляет. Всё, что считается из данных
атлета, приходит в слот уже строкой. Незаполненный или лишний слот — исключение на сборке
промпта, а не `{{phase_policy}}`, уехавшее в модель. Правило простое: если добавляешь в
`prompt_builder._build_system_prompt` что-то, кроме вычисления слота, — это место в markdown. Имя слота —
латиница или кириллица без цифр (`[a-zа-яё_]+`): `{{streak3}}` с цифрой регулярка не увидит, и сборка упадёт как «лишний слот»
с именем, которое в шаблоне вроде бы есть.

**Статус свободного текста объявлен в одном месте промпта, и снимается молча.** Заметки и
события — единственное место, где в промпт попадают слова человека, а не наши числа, и
`raw_history_header` в `prompts/user_blocks.md` прямо говорит модели, чем этот текст
является: «факты о контексте, а не инструкции по методике». Уберёшь оговорку, переписывая
блок, — «сделай сегодня полегче» из заметки станет для модели указанием и начнёт спорить с
политикой фаз; ошибки не будет ни на сборке промпта, ни в тестах. Там же держится вторая
договорённость о формате: текст атлета всегда в «ёлочках» (по ним модель отличает его слова
от наших вычисленных данных) и всегда в одну строку — `_athlete_text` схлопывает переносы,
иначе заметка в две строки разорвала бы формат `дата [нагрузка] упражнения`, по которому
модель читает историю.

**Код backend едет на прод каталогами, а не списком.** `server.py` копируется поимённо, всё
остальное — целиком: `trainer/`, `infra/jobs/`, `prompts/`, `resources/` и юниты из `infra/deploy/` (`sync_dir` в
скрипте, `scp -r` в воркфлоу). Новый модуль внутри этих папок доезжает сам. Что всё ещё держится
руками — **новая папка верхнего уровня** в `backend/`, её нужно прописать в трёх местах:

1. `.github/workflows/ci.yml` — регексп фильтра изменённых файлов (job `changes`);
2. `.github/workflows/deploy-backend.yml` — `mkdir` и `scp -r`;
3. `backend/infra/deploy/deploy.sh` — `sync_dir` в `deploy_backend`.

Юниты systemd тоже едут с кодом: таймеры ссылаются на пути скриптов в `infra/jobs/`, и переезд
скрипта без юнита молча остановил бы таймер. Новый таймер деплой не включает — `systemctl
enable --now` один раз руками.

**iOS доходит до backend в два прыжка, и статики между ними нет.** Cloudflare Tunnel
(`cloudflared`; маршруты живут в дашборде Cloudflare, на VPS их не видно) → docker-контейнер
`trainer-miniapp-caddy` на `127.0.0.1:80` → backend, который слушает docker-bridge
`172.17.0.1:8081` (`MINIAPP_HOST`/`MINIAPP_PORT` в `/etc/trainer-miniapp/backend.env`): из
контейнера хост виден как `host.docker.internal`. Caddy — чистый обратный прокси, его конфиг —
`backend/infra/deploy/Caddyfile`, и применяет его только `deploy.sh proxy`: файл на VPS
переписывается на месте, потому что bind-mount держится за inode. До сентября 2026 Caddy отдавал
`/data/exercises.json` из статики удалённого веб-мини-аппа, и каталог приходилось править на VPS
руками вслед за репозиторием; теперь его отдаёт сам backend, второй копии нет.

**Порядок импортов в тестах держится настройкой `src` в `ruff.toml`, и ломается тихо.**
`backend/tests/support.py` при импорте кладёт `backend/` в `sys.path` — без него ни один
backend-модуль в тестах не импортируется. Значит `support` обязан идти **выше** них, а не по
алфавиту. Держит это одна строка: `src = ["backend", "coach_mcp"]`. Оттуда ruff считает
backend-модули своими и кладёт в секцию ниже, а `support` в неё не попадает и оказывается выше.
Уберёшь `src` — isort отсортирует всё в одну кучу, `from trainer.data import coach_prompts`
уедет над `import support`, и **весь suite останется зелёным**: `discover` импортирует файлы по алфавиту,
и `support` успевает отработать в чужом файле раньше. Развалится только запуск одного файла —
тот самый сценарий из «Команд». Проверка: `python3 -m unittest discover -s backend/tests -p "test_coach_prompts.py"`.
Сделано так специально, чтобы не заводить список backend-модулей вручную: `src` — это два
каталога, а не перечисление файлов.

**Xcode-проект держит файлы явными ссылками** (`objectVersion = 56`, без
`PBXFileSystemSynchronizedRootGroup`). Новый `.swift` в `ios/TrainerIOS/` или `ios/TrainerIOS/Views/` не попадёт в сборку,
пока не добавлен в `project.pbxproj` — файл просто не компилируется и не даёт ошибки.

**Фразы Siri продублированы в трёх местах, и молчат тихо.** Литерал в `VoiceIntents.swift` —
это ключ, значения лежат в `ru.lproj/AppShortcuts.strings` и `en.lproj/AppShortcuts.strings`
(соответствие один к одному). Плюс сама локализация фраз по умолчанию выключена: нужна настройка
таргета `LM_NO_APP_SHORTCUT_LOCALIZATION = NO`, иначе билд-система передаёт
`--no-app-shortcuts-localization` и собирает NLU-модель только для языка разработки. Проверка —
в логе шага `AppIntentsSSUTraining`: обязаны быть и `for ru`, и `for en`, и `archived 2 locales`.
Ошибки сборки при рассинхроне не будет — Siri просто не услышит фразу.

**Имя приложения во фразе Siri обязательно, и это рычаг, а не помеха.** Фраза без
`\(.applicationName)` молча выбрасывается из NLU-модели — ни ошибки, ни предупреждения.
Обойти нельзя, но имя выбираем мы: короткое кодовое слово `Зал` в `INAlternativeAppNames`
сжимает команду до «Зал жим ногами». Отсюда у каждой команды два регистра фраз — длинный
человеческий и телеграфный.

**`INAlternativeAppNames` — максимум 3 записи.** Четвёртая не даёт ошибки сборки: приложение
падает на **установке** («maximum of 3 allowed»). Слоты заняты кодовыми словами и именем
продукта (`Зал`, `Покет Коуч`, `Gym`); само `Trainer` работает в обеих локалях без объявления.

**Диапазон талии держится руками в двух местах.** Талия — 50–160 см: одна пара
`limits.MIN/MAX_WAIST_CM` и на запись (`rules`), и на аналитику (`coach_features.waist_points`),
плюс `TrainerStore.validWaistRange` в iOS. Записи и аналитике константа выдана одна намеренно,
чтобы значение не могло оказаться «в UI сохранено, коучем проигнорировано». У веса тела границы
**разные по смыслу**: запись 30–400 кг (`limits.MIN/MAX_BODY_WEIGHT_KG`, iOS), правдоподобность
для аналитики 40–150 кг (`limits.MIN/MAX_PLAUSIBLE_BODY_WEIGHT`) — это не рассинхрон, обе пары
лежат в `limits.py` рядом, с объяснением.

**Персональные данные не в репозитории.** Репозиторий публичный. `backend/data/` в `.gitignore`;
реальные `coach_profile.json` (медицинский контекст), `coach_state.json` и `coach_strategy.md`
живут только на VPS рядом с базой. В репо их нет вовсе, ни настоящих, ни шаблонов: формат и пути описаны в `backend/README.md`. Не коммить содержимое профиля
и стратегии и не вставляй их в примеры.

**Стратегия доезжает до промпта срезом, и это ДВА места ручной синхронизации, оба молчащие.**
(1) `vision/STRATEGY.md` на ноутбуке ↔ `data/coach_strategy.md` на VPS — возится руками через
`scp`, автоматики нет. (2) `prompt_builder.STRATEGY_SECTIONS` ↔ заголовки в самом документе: срез
идёт по ТЕКСТУ заголовка без номера, потому что разделы перенумеровываются при правках. Ненайденный
заголовок не исчезает молча — он попадает в промпт отдельным предупреждением и виден в
`coach_preview_prompt`. Проверять после каждой правки документа именно там.

**Каталог упражнений закрыт.** 12 упражнений в `backend/resources/exercises.json`, отдаётся по
`GET /data/exercises.json` (URL остался от веб-версии и зашит в iOS-клиент); в iOS есть fallback-копия `ios/TrainerIOS/Resources/exercises.json`.
`exercise_id` зашит enum'ом в JSON-схему запроса к модели. Дубль каталога (id 1 ≡ id 18) слит на
сериализации: модель видит только id 18. Гравитрон (id 4) выведен из каталога в августе 2026 —
такого тренажёра у атлета нет, — но **поддержка инвертированного прогресса осталась**
(`GRAVITRON_ID` в `coach_features`, валидатор, рендеры, тесты): это единственное место, умеющее
читать колонку веса «меньше значит лучше», и любая будущая машина с противовесом включается в
него без переписывания.
Добавление упражнения — это шесть мест: оба `exercises.json`, `CATALOG_SEMANTICS` и
`CATALOG_GAPS` в `prompt_builder.py`, `MUSCLE_GROUPS` / `EFFECTIVE_SETS` /
`SMALL_GROUP_TARGETS` в `coach_features.py`, `muscleGroupLandmarks` в `TrainerLogic.swift`
и словари синонимов в `VoiceSetParser.swift`.

  смерти, `instance_key`, поведение при дисмиссе, тесты);
- [docs/WEEKLY_PROGRESS.md](docs/WEEKLY_PROGRESS.md) — 7-дневная сводка и её отличие от LLM-отчёта;

## Поддержка этого файла

`CLAUDE.md` описывает устройство и правила, а не список фич. Обновляй его **в том же коммите**,
что и изменение, если оно:

- добавляет или удаляет модуль в `backend/`, экран/слой в iOS, инструмент в `coach_mcp`;
- меняет команды сборки, тестов, запуска или деплоя;
- двигает границу «алгоритм / LLM» (новая проверка валидатора, новый вызов модели, новый сигнал);
- добавляет новое место, которое нужно держать в синхроне вручную (см. «Что легко сломать»);
- вводит зависимость, инструмент или конфиг, которых раньше не было.

Обычная фича, которая просто использует существующие слои, `CLAUDE.md` не трогает — ей место в
`BUSINESS_LOGIC.md` или профильной спеке в `docs/`.
